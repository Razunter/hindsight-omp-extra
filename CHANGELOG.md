# Changelog

## Unreleased

- Fix: `hindsight_evidence` accepted only `action` plus the one field the action uses, so models that send both `query` and `id` (one empty) got `invalid_input` on every call. The unused field may now be omitted or empty; a non-empty unused field, a missing required field or any other key is still refused.
- Local Hindsight management is now opt-in and Off by default, including for existing installations, which get a one-time notice. Off does no Docker work and no provider-file validation, never stops the running container and leaves provider files, selection and credentials untouched. Evidence, recall guidance and ingestion work without local management.
- New `/hindsight` menu with Status, Mode (Off/CPU/GPU), Provider configuration, Apply requested configuration, Apply available update and Check for updates. It replaces `/hindsight-provider`, which is removed without an alias.
- Applying CPU management shows one confirmation with the exact image (cached image ID or `repository@digest` download), the configuration and the shared-service cutover, then runs in the background in the current OMP process. There is no download-only step. The current container keeps running during the download and until a graceful stop (up to 75 seconds); the replacement reuses the same volume, credential mount, ports, bind address and worker identity, and counts as active only after `/health` reports a healthy API and connected database. A failed launch restores the previous container; a failed readiness check keeps it and both images for a manual decision. A version change warns that the reused database may be migrated and that the old image is no rollback.
- First installations and updates download the approved target by registry digest after that approval: a first apply without a cached image checks the registry, and a missing approved image is offered through the same apply. A tag or check that moves after approval cannot change the applied image. Downloaded images are recorded as owned. After a healthy cutover the configured tag moves to the new image.
- With CPU or GPU management on, startup starts the stopped approved container or recreates a missing one from the approved cached image and configuration. Pending configuration, a missing image or an unrecognized container are reported, never applied.
- The official `ghcr.io/vectorize-io/hindsight:latest` configuration now checks and updates to the latest stable GitHub release's versioned Docker image. Update notices and Status include its version and release-page URL. Failed release discovery never falls back to the moving tag. Explicit version tags, digest pins, and custom references retain their targets. Checks remain metadata-only, paced at once per day on startup, and available immediately through **Check for updates**. Downloads, GPU rebuilds, and runtime replacement still require approval.
- Lifecycle operations across OMP processes are coordinated through `.local-management.json` under a lock that only its holder releases and whose stale-lock recovery is serialized; an approval is revalidated before any download or build and again before cutover, including against a runtime another process applied meanwhile.
- **Apply requested configuration** keeps the approved upstream image, so a provider or mode change can be applied while an update is pending; **Apply available update** applies the update the last check recorded.
- Opt-in GPU mode for the local embedding and reranker models, never selected automatically. One approval names the upstream `repository@digest` and builds, in the background, an extension-owned CUDA derivative (`hindsight-omp-cuda:<digest prefix>-<recipe hash>`, about 11 GB) from a context holding only a generated Dockerfile adapted from Hindsight's CUDA recipe: same torch version with CUDA 12.6, `uv pip check`, no other package changed. The derivative also installs a C compiler, which Triton needs for some local models on CUDA. Before cutover a throwaway `--gpus all` container with the configured environment must run one inference of every local model on CUDA; the new container runs with `--gpus all` and is ready only when the same probe, run in it with `docker exec`, reports CUDA for every local model. Prerequisite, build, validation and readiness failures keep the current service and leave GPU visibly requested and failed, with no CPU fallback. The derivative is recorded as owned with its base and recipe, reused on restarts and later approvals while both match, and rebuilt only through an approved apply or update. GPU needs the NVIDIA driver and NVIDIA Container Toolkit; CPU mode needs neither.
- After a healthy cutover only, superseded images are removed: the previously active image and recorded downloads and CUDA derivatives that are not the active image, another operation's candidate or of the active upstream release, including derivatives left by earlier updates. Ownership labels, other tags and containers (running or stopped) are checked again right before each `docker image rm --no-prune`; nothing is forced or pruned, and build cache, volumes and credentials are untouched. A failed removal is a warning naming the image and a separate cleanup failure in Status while the runtime stays ready; the next clean run clears it. Failed builds, validations, launches and readiness checks remove nothing. Shared layers and build cache can keep disk space allocated after removal.
- Removed automatic image pulls, the `.last-image-check` file and automatic container recreation on configuration drift.
- With a tool named `observe` active (skill-observer), the memory-quality block in main Hindsight sessions asks the agent to record an observation with `observe` when injected memories repeat one fact, a mental-model snapshot is truncated, or a recalled claim proved wrong and a saved correction cannot retire it. The line appears with or without a lesson tool. `observe` results do not advance the recall-nudge interval.
